# 数据飞轮设计方案:风格进化(多用户)

> 状态:方案稿,待所有者裁决与外部评审;未做任何工程实现。
> 目标(所有者已定):**能力进化**——AI 生成的风格与用户的要求随使用越来越符合。
> 部署假设:**面向多用户**。

## 0. 一句话

用户用得越多,系统越懂这个用户:把分散在各处的人工反馈**持续蒸馏**为可注入
生成链路的风格规则,经**人工准入**后回注,并用指标证明飞轮真的在转。

## 1. 北极星与指标口径(数字纪律:全部实测,基线先于建设)

| 指标 | 定义 | 说明 |
|---|---|---|
| **指令复发率**(北极星) | 某 directive 被蒸馏为 active 规则并回注后,同性质新指令出现的比例 | 飞轮转动的直接证据:系统学会了,用户就不必重复自己。防恒真:须与首过率同看(用户放弃也会表现为不再提) |
| 评审首过率 | 章节质量评审一次通过、无需重写的比例 | 已有数据(review_results),按时间窗对比 |
| 重写循环深度分布 | 每章触发评审-重写循环的次数分布 | 已有口径,复发率下降应伴随之下降 |
| 风格符合度 | LLM-judge 按该用户 active 规则逐条比对生成文本的符合率 | judge 提示与规则同源,存在自评偏差 → 见 §7 风险 |
| 规则命中率 | 注入的规则在生成中实际可追溯生效的比例(style_injections 归因) | 甄别"注入了没用"的死规则,供淘汰 |

**基线纪律**:P0 先在现有数据上把指令复发率/首过率的当前值测出来,任何
改造后的对比才有意义。

## 2. 飞轮五段:采集 → 归纳 → 准入 → 回注 → 验证

```
        ┌────────────────────────────────────────────┐
        │                  ⑤ 验证                    │
        │   复发率↓ 首过率↑ 命中率 死规则淘汰         │
        └───────▲────────────────────────────────────┘
                │              ④ 回注
   ┌────────┐   │   ┌──────────────────────────┐   ┌────────┐
   │① 采集  ├───┴──►│ ② 归纳(离线蒸馏,便宜档) │──►│③ 准入  │
   │人工信号 │       │ 事件聚类→候选规则生成     │   │审核队列 │
   └────────┘       └──────────────────────────┘   └───┬────┘
        ▲                                              │ active
        │              用户继续使用、继续反馈            │
        └──────────────────────────────────────────────┘
```

### ① 采集(现状:大部分已在落库,缺三块)

| 信号 | 现状载体 | 性质 |
|---|---|---|
| 用户定向指令 | `user_directives` | 显式偏好,最高质量 |
| 评审拒绝及理由 | `review_results`(人工复核段) | 显式负样本+理由 |
| 事实/实体审核 | `facts` / `entity_merge_proposals` 的 reject | 二值人工标注 |
| 大纲/细纲确认时的修改 | 中断点 resume payload | 稀疏但权威 |

**缺口(需补采集)**:
a) 章节审阅如果只有"通过/打回"而没有逐条修改意见,负样本没有理由,蒸馏
   无从下手——需要在审阅卡提供结构化意见输入(或文本编辑,diff 即信号);
b) `user_directives` 目前没有与后续 run/章节的回链,无法判断"这条指令是否
   已被吸收"——需补 run_id/chapter_no 关联与"已处置"状态;
c) 隐式信号(用户对生成文本无修改直接过审 = 接受)目前即"confirm",可复用,
   但需与"放弃"区分(连续多章无反馈+停止使用,不算正面信号)。

### ② 归纳(离线蒸馏,不碰生成主链路)

- 触发:按量/按批(如每积累 N 条未处置事件,或 run 空闲时),不阻塞生成。
- 机制:便宜档模型(CHARACTER/SUMMARY 路由档)把未处置事件聚类,归纳为
  **候选规则**,每条规则必须携带溯源(source_events 引用原始事件 id)。
- 归纳的输出是"候选",不是"生效"——生效只发生在 ③。
- 主题分层见 §3,确保规则注入到正确的 Agent。

### ③ 准入(人工锚定——飞轮不自转的保险丝)

- 候选规则进**审核队列**,复用产品已有的 pending_review 队列模式
  (facts/entities 同款交互):通过/拒绝/编辑后通过。
- **无人工准入的规则永不回注**。这是防自证漂移的唯一硬闸(§7)。
- 规则被通过时记录 confirmed_at;此后每次生成"按该规则执行且未被用户
  再纠正"即刷新其账龄(再确认机制,§4)。

### ④ 回注(按分层注入对应 Agent,带归因)

- 规则块以紧凑清单形式注入 prompt(每条一行),并写 `style_injections`
  (rule_id, run_id, chapter_no, agent_role)——没有归因就没有 §1 的命中率
  与复发率口径。
- token 成本:每章注入约等于一个小清单(几十~几百 token),受每日预算
  闸门统一约束;规则容量上限本身就是成本上限。

### ⑤ 验证

- 复发率:新 directive 到达时,先由蒸馏 job 判定其是否可被某条 active
  规则解释;可解释 = 复发。复发规则不是失败——区分"规则缺失"(新问题)
  与"规则失效"(已有规则没被执行,查 injection 归因)。
- 命中率与死规则:连续 K 次注入且无可追溯影响的规则标记 retired(淘汰,
  不是删除,保留审计链)。
- 全量回归:143 项测试 + replay 评测不回归是任何回注机制上线的底线。

## 3. 风格画像分层(与 11 角色路由对齐)

"风格/要求"不是一个东西,分三层,各注入各自负责的 Agent——注错层=无效注入:

| 层 | 内容示例 | 注入对象 |
|---|---|---|
| 文风层 | 短句/少形容词/打斗节奏快/对白占比 | **POLISH**(文风精校,便宜档,ADR-0018)+ WRITER |
| 叙事偏好层 | 多线并进/每章末留钩子/反派视角戏份 | WRITER + OUTLINE(影响细纲) |
| 设定偏好层 | 不写后宫/力量体系保持克制/伏笔密度 | OUTLINE(大纲裁决)+ 伏笔治理参数 |

规则条目 schema 草案:

```
style_rules(
  id, scope TEXT,            -- story | user(多用户见 §5)
  owner_user_id, story_id,   -- 归属与隔离边界
  layer TEXT,                -- style | narrative | setting
  statement TEXT,            -- 单句可执行,如"对白占比不超过三成"
  status TEXT,               -- candidate | active | retired
  priority INT,              -- 冲突消解:新压旧 + 层内显式优先级
  source_events JSON,        -- 溯源:原始事件 id 列表
  confirmed_at, last_hit_at, -- 账龄 = 未再确认时长
  hit_count, miss_count      -- 命中率口径
)
```

## 4. 治理闸门(每一条都有前车之鉴或行业教训)

| 闸门 | 规则 | 鉴于 |
|---|---|---|
| 人工锚定 | 无准入不入注 | LLM 自评闭环自证漂移(model collapse) |
| 容量上限 | 单 story active 规则 ≤20,单用户聚合 ≤40 | 动态黑名单死循环(ch12 实证);prompt 膨胀 |
| 账龄淘汰 | last_hit_at 超线(如 20 章)自动 retired | 过时规则变负资产(设定改了规则没改) |
| 冲突消解 | 同层互斥规则:新 confirm 压旧,旧的转 retired | 用户口味会变,飞轮不能变成沉积层 |
| 注入审计 | 每次注入必写 style_injections | 没有归因,所有指标口径都不成立 |
| 预算联动 | 规则注入计入每日 token 预算 | 已有闸门(story/global)统一约束 |

## 5. 多用户 schema 与隔离

- **原始事件不另建表**:`user_directives`/`review_results`/`facts.reject`
  已是采集层,补缺口字段(§2①)即可,避免同数据双源。
- **新表两张**:`style_rules`(上)、`style_injections`(rule_id, run_id,
  chapter_no, agent_role, created_at)。
- **隔离模型**:规则归属 owner_user_id(+可选 story_id);user 级规则是
  用户自己的资产,**跨用户永不混用**——与 stories/story_members 同构的
  ACL 边界,不引入"全局众包规则池"(多用户偏好互相污染是无法审计的质量
  事故;若未来要做,是显式的新决策)。
- **迁移**:版本化迁移(v8),沿用 schema_migrations 机制。
- **冷启动(多用户特有)**:新书无规则时回退现状(零注入,行为不变);
  可选引导:创建故事时让用户选风格模板(预置只读全局模板,不属于任何
  用户),用户后续 directive 逐步覆盖模板项。
- P3(远期):用户开新书时,其 user 级 active 规则作为候选种子带入,
  加速冷启动——仍走该书的准入确认,不静默生效。

## 6. 分期路线(方案获批后按此排期,每期独立可验收)

| 期 | 内容 | 验收 |
|---|---|---|
| P0 指标基线 | 在现有库上测出复发率/首过率当前口径;确定 directive 归类判定器 | 基线报告(零 token 判定可用规则法,实测口径) |
| P1 采集+准入 | 补三块采集缺口;style_rules 表+迁移;候选蒸馏 job;规则审核队列 UI | 一条 directive 能走完 采集→候选→人工通过 全链 |
| P2 回注+验证 | 分层注入+injection 归因;复发率/命中率看板;死规则淘汰 | 基线 vs 注入后对照报告;143 测试+replay 不回归 |
| P3 用户级聚合 | user 级规则、跨 story 冷启动种子 | 多故事用户复发率对照 |

## 7. 风险清单

| 风险 | 缓解 |
|---|---|
| 自证漂移(模型欣赏自己) | ③ 人工准入硬闸;few-shot 类资产(若做)只收人工过审未改动文本 |
| 规则雪崩/死循环 | 容量上限+账龄淘汰;黑名单事件的设计复盘已内化为闸门表 |
| judge 自评偏差 | 风格符合度只作辅助指标,北极星是指令复发率(人工行为,不可自欺) |
| 复发率口径被误读 | 与首过率联动解读;区分规则缺失/规则失效(§2⑤) |
| 用户隐私 | 规则/画像属用户资产,租户隔离同 ACL;跨用户混用被显式禁止 |
| 成本失控 | 蒸馏走便宜档离线;注入计入既有预算闸门;规则容量即成本上限 |

## 8. 未决问题(需所有者裁决)

1. **章节审阅的反馈粒度**:加结构化意见输入,还是提供文本编辑(diff 即
   信号)?前者工程小,后者信号最丰富但改工作台交互。
2. **蒸馏触发节奏**:按量触发(如每 30 条未处置事件)还是定时批处理?
   单机部署下两者都可行,影响的是"规则生效延迟"。
3. **风格模板库**:P1 是否附带预置模板(网文常见流派文风),还是完全从
   用户反馈冷启动?
4. **复发判定的成本口径**:directive 归类判定用规则法(零 token,粗)还是
   便宜档 LLM(准,有成本)?P0 基线建议规则法,P1 起再议升级。
